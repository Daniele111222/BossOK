## 2. 每项任务的交付与完成条件

### T00：验证两部设备的安装与联网

**交付**：实际目标手机能安装最小应用，首页访问真实健康检查；确定是否需要安卓、鸿蒙分别构建。

- [ ] 记录两部手机型号、系统版本、构建与签名方式。
- [ ] 使用手机可达地址访问健康检查，记录安装与联网证据。
- [ ] 列明需要的平台权限、签名/推送条件及已遇到的问题，不把 H5 验证替代安装验证。
- **验证**：A14 的前期部分；T00 完成不代表 R11 整体完成。

### T01：登录与两人绑定

**交付**：按确认的账户创建规则，双方可登录、退出、邀请码绑定，页面显示可信角色与共享关系。

- [x] identity、共享契约和手机页面协同完成真实身份流程，不内置生产默认密码。
- [x] 密码安全哈希，会话可失效，邀请码按约定单次使用且有有效期。
- [x] 未登录、过期会话、错误邀请码和跨关系访问有明确处理，角色不能由客户端自行提升。
- [x] D01、D02 的决定记录到需求池；不擅自增加开放注册、重置密码或解绑功能。
- **验证**：A01、A02；测试可信身份与权限，不只测试按钮隐藏。

### T02：约定预算与显示额度

**交付**：审批人设置日、月预算及分类口径，双方首页看到一致预算和生效信息。

- [x] 服务端验证金额、角色和生效日期，持久化预算历史。
- [x] 预算未设置时显示明确入口，不默认填入示例预算。
- [x] 固定支出适用口径、修改生效与跨月策略按 D03、D04 执行。
- **验证**：A03、A04；只显示预算时即可演示，不依赖先完成审批。

### T03：记账并更新剩余额度

**交付**：申请人填金额、分类、日期和备注后，双方账本与首页同时反映实际支出。

- [x] 提供写入契约、服务端校验、真实账本查询和客户端录入，不以假数据占位。
- [x] 相同创建请求重试不重复记账，失败保留输入，成功后刷新。
- [x] 未审批实际超支照实录入并标记，不能因额度不足丢弃真实消费。
- [x] 列表支持产品要求的月份和分类筛选，服务端限制查询范围与返回规模。
- **验证**：A05，以及 A03、A04 的支出更新部分。

### T04：维护账目与退款

**交付**：补记、更正、删除和关联退款后，双方看到修正后的账目、历史变更和额度。

- [x] 删除可追溯，变更与退款归属规则依 D05、D08。
- [x] 防止无权限修改、重复退款及已确认不允许的超额退款。
- [x] 不把退款当独立收入或额外节省奖励；按口径修正历史净支出。
- [x] 审批关联账目不得因更改而绕过已批准金额；为 T06 保留已明确的不变量。
- **验证**：A06；T06 关联账目上线时补齐关联变更的回归场景。

### T05：申请与审批闭环

**交付**：申请人超预算时发起申请，审批人看到预算与未消费承诺后作决定，双方列表同步状态并有应用内消息。

- [ ] 超日、超月或同时超预算正确展示，一笔消费只产生一份申请。
- [ ] 同意、拒绝、撤销和金额变更重提严格遵循状态与角色约束。
- [ ] 已同意但未消费不扣实际支出、不修改预算。
- [ ] 状态更新与应用内消息同事务写入；重复或并发审批不产生冲突的双结果。
- [ ] 批准占用完整预计金额，当日过期释放占用；跨日购买重申，真实当日消费可补记；详情与列表显示已过期状态。
- **验证**：A07、A08、A13 的应用内待审批/审批结果部分。

### T06：实际消费确认

**交付**：批准后购买可填实际金额，一次确认对应一笔账目；不购买可取消。

- [ ] 权限校验、状态迁移、唯一账目和应用内消息在同一事务中成功或回滚。
- [ ] 相同请求重试、连续点击、两端并发不重复扣费或生成记录。
- [ ] 超额实际消费如实记账，差额补批不重复生成支出；修改日期不转移批准，有退款记录不删除。
- [ ] 仍允许记录已经发生的未批准超支，并展示其真实状态。
- **验证**：A09、A10，回归 A06、A08。

### T07：自动结余反馈

**交付**：月度汇总自动展示按已录入账目计算的累计结余、负值超支、达标天数与分类信息。

- [ ] 排除当天及预算生效前日期，无账目日按零支出，不增加每日确认操作。
- [ ] 扣掉超支日，忽略未消费或拒绝申请的金额；不等同于真实存款。
- [ ] 补记、修改、删除与退款重算，历史额度使用当时适用版本。
- [ ] 显示统计口径及简单鼓励文案，空状态不捏造节省金额。
- **验证**：A11、A12；T06 上线后回归批准消费正常进入净支出。

### T08：完整消息提醒

**交付**：待审批、审批结果与预算提醒具备应用内记录及约定的手机提醒体验。

- [ ] 按 D09 实现阈值、偏好与重复提醒规则，数据库消息不依赖推送到达才可见。
- [ ] 目标设备前台、后台、权限关闭和投递失败有可验证结果；不能保证必达或强制打开系统权限。
- [ ] 远程投递在事务后执行，失败记录可恢复，不能撤销已经完成的审批。
- [ ] 通知点击后重新请求状态，不信任通知中缓存的旧结果。
- **验证**：A13 全部；审批结果记录依赖 T05，预算阈值依赖已具备的 T02、T03。

### T09：签名包与双机业务验收

**交付**：两部目标手机安装候选签名包，访问同一测试服务并跑通业务闭环。

- [ ] 实际验证登录绑定、预算、记账、审批、消费确认、统计、提醒与同步。
- [ ] 覆盖升级保持应用可用、账户和服务端数据一致，签名及证书安全备份。
- [ ] 记录安卓/鸿蒙各自构建方式、版本、设备和结果，不以资源编译成功冒充可安装包。
- **验证**：A14 全部，记录 A01—A13 的双角色现场结果。

### T10：部署与最终交付

**交付**：候选版本在已有服务器上以单实例容器部署，使用已有域名与 HTTPS，持久化数据库目录，部署可重复，备份能恢复。当前先本地开发，不执行上线操作。

- [ ] 容器包含 Node 24、构建产物、契约、运行依赖和迁移，环境变量注入配置；挂载整个数据目录，容器重建不丢数据，密钥不进镜像或仓库。
- [ ] 每日备份保留 7 天，至少一份独立存储；恢复演练验证数据、历史预算与审批关联，最多损失 24 小时数据且 24 小时内恢复。
- [ ] 核实依赖风险适用性并处理发布阻断项，历史审计结果不代表已清零。
- [ ] 执行 A00—A15，记录通过、失败、未执行与遗留项，交付运行/升级/恢复说明。
- **验证**：A15，并复核其余场景的证据完整性。
