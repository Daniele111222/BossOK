# 老板批了：需求池

- 日期：2026-10-23
- 来源：[核心产品需求](./核心产品需求.md)、[架构设计](./架构设计.md)及当前源码。
- 优先级为建议开发顺序，不代表删减已确认范围或承诺交付时间。

## 1. 状态定义

| 状态 | 含义 |
| --- | --- |
| 已完成 | 已存在实现与验证证据，且仅针对列明范围 |
| 待开发 | 范围已确认，但尚无完整实现 |
| 待细化 | 范围已确认，包含会影响实现或验收的未定规则 |
| 后续候选 | 未纳入第一版，不自动排期 |
| 不纳入 | 当前明确不做 |

P0 为核心业务闭环；P1 为完整第一版的反馈、通知与交付条件，仍须在正式验收前完成。

## 3. 待确认决策

以下均未确认，不给实现填入隐含默认值。建议仅供后续评审，决定后记录选择与日期。

| 编号 | 待决定内容 | 为什么影响交付 | 建议供评审 |
| --- | --- | --- | --- |
| D01 | 首次账户如何创建，角色如何确定，忘记密码如何处理 | 防止自行冒充审批人，明确 T01 入口 | 自用第一版优先考虑受控创建两人账户；不开放无约束注册 |
| D02 | 绑定后是否可换人、解绑，历史账目对双方如何可见 | 影响关系权限、共享提示及历史查询 | 本期可先不提供主动解绑入口；如需解绑须先定义数据策略 |
| D03 | 首次预算生效日期、调整何时生效、跨月预算如何产生 | 影响历史日额度、累计结余与月度归属 | 日额度修改从次日生效；月预算修改保留版本，不追改历史 |
| D04 | 哪些固定支出分类不计日额度，谁可修改分类口径 | 影响超支计算及是否可绕过审批 | 由审批人按双方约定维护，历史记录保留适用口径 |
| D05 | 退款归属日期、跨月退款、部分/多次退款和超额退款规则 | 影响历史统计及退款约束 | 建议累计退款不超过原支出；跨月口径单独确认 |
| D06 | 已批准未消费申请是否占额度，是否防止多笔承诺超过预算 | 影响申请时的可用额度和审批展示 | 先明确承诺总额与实际支出的区别，再决定占用逻辑 |
| D07 | 申请有效期、消费日期变更与跨日处理 | 影响申请是否仍可消费，是否重新审批 | 跨日后重新判断额度；不预设自动延用批准 |
| D08 | 已消费关联账目的修改、删除、退款怎样保持审批记录一致 | 防止改单后绕过批准金额或产生悬空申请 | 保留原申请与变更轨迹；金额增加重新审批，具体流程待定 |
| D09 | “接近预算”阈值、通知偏好、重复提醒规则和推送接入 | 影响提醒验收和后台到达方式 | 优先复用现有通知方案，阈值确认后写入规格 |
| D10 | 双方手机型号、完整系统版本、分发与签名方式 | 决定 APK 或鸿蒙独立交付及可安装性 | 先用最小应用验证两部手机 |
| D11 | 服务地址、部署位置、备份位置与恢复目标 | 决定真实同步、持久化和交付验收 | 单实例 HTTPS，备份与数据同机失效不能视为可恢复 |

依赖决策的任务仍可准备不受影响的测试或设计，但不能把“建议”当作确认结果完成受影响的实现。
