# 老板批了：第一版功能规格

- 日期：2026-10-23；状态：草稿，供实现前评审。
- 范围与编号见 [需求池](./需求池.md)，架构归属见 [架构设计](./架构设计.md)。
- D 编号为未定规则，不能作为自动采用的默认配置。本规格没有声明业务能力已完成。

## 1. 问题与解决方案

申请人难以持续控制日常消费，审批人缺少可查看的预算与花销记录。应用通过两人共享预算、及时记账、超支前申请和事后实际消费确认，建立可追溯的消费约定；自动结余反馈展示按已录入账目少花了多少钱。

独立应用无法拦截外部支付，允许记录已发生但未审批的真实支出；预算结余也不表示银行账户中真实存款。

## 2. 用户故事

1. 作为申请人，我希望登录自己的账户，以便账目属于正确的人（R01）。
2. 作为审批人，我希望通过邀请码绑定双方，以便只查看约定共享的数据（R02）。
3. 作为双方用户，我希望知道数据共享范围，以便理解谁能看到消费记录（R02）。
4. 作为审批人，我希望设置日额度和月预算，以便执行双方约定（R03）。
5. 作为申请人，我希望查看今日和本月剩余预算，以便决定下一笔消费（R03）。
6. 作为申请人，我希望快速记录金额、分类、日期和备注，以便减少漏记（R04）。
7. 作为申请人，我希望更正、补记和记录退款，以便统计反映真实支出（R05）。
8. 作为审批人，我希望查看账目变更，以便了解花费为何变化（R05）。
9. 作为申请人，我希望在超过日或月预算时提交一次申请，以便说明用途和原因（R06）。
10. 作为审批人，我希望同时看到预算和已批准未消费申请，以便判断新申请（R07）。
11. 作为申请人，我希望知道审批结果并能撤销待审申请，以便避免重复沟通（R06、R07）。
12. 作为申请人，我希望购买后按实际金额确认，并自动生成关联账目，以便不重复记账（R08）。
13. 作为申请人，我希望没购买时取消消费，以便未花的钱不计为支出（R08）。
14. 作为申请人，我希望实际超支仍能如实记账，以便不因流程限制而隐瞒支出（R04、R08）。
15. 作为申请人，我希望看到累计结余与达标天数，以便获得节约的成就感（R09）。
16. 作为双方用户，我希望收到提醒并在两台手机看到一致结果，以便及时处理审批（R10、R11）。

## 3. 页面与异常交互

| 页面 | 主要操作 | 必需状态 |
| --- | --- | --- |
| 首页 | 今日/月度额度、记一笔、申请超支 | 未登录、未绑定、未设置预算、加载、真实数据、失败可重试 |
| 账本 | 按日/月和分类查询、录入、更正、退款、查看变更 | 空账本、筛选无结果、提交中、失败保留输入、成功刷新 |
| 审批 | 申请列表/详情、审批意见、撤销、取消消费、确认消费 | 待审、已拒绝、待消费、已消费等状态；权限不足与并发冲突 |
| 月度汇总 | 累计结余、超支、达标天数、分类汇总 | 未设置预算、不适用日期无统计、零支出与负结余；注明按已录入账目统计 |
| 我的 | 登录/退出、绑定、角色、预算与提醒设置 | 账户过期、邀请码失效、角色权限、未定操作不放假入口 |

提交中避免重复点击，成功以服务端响应为准。网络失败保留输入，不自动重试创建类操作；使用同一请求标识重试时必须由服务端保证不重复创建。返回前台和完成操作后刷新相关数据，不依赖后台持续连接。

## 4. 权限与 Module 归属

| 操作 | 申请人 | 审批人 | 说明 |
| --- | --- | --- | --- |
| 查看绑定内预算/账目 | 是 | 是 | 其他关系的数据不可访问 |
| 设置预算和约定分类口径 | 否 | 是 | 保留变更原因与历史版本 |
| 维护自己的支出与退款 | 是 | 否 | 审批人只查看；关联账目维护依 D08 |
| 发起/撤销自己的申请 | 是 | 否 | 撤销只适用于待审批 |
| 同意/拒绝申请 | 否 | 是 | 不允许同一申请重复处理 |
| 确认或取消消费 | 是 | 否 | 只适用于已批准未消费申请 |
| 查看共享变更及统计 | 是 | 是 | 共享范围依绑定关系规则 |

角色来自 identity Module 的可信身份上下文，客户端输入不能直接授予角色。每次读写都验证身份、关系和操作者，不能只依赖前端显示限制。身份创建与解绑按 D01、D02 细化。

`spending` Module 内组织预算、支出、申请与查询，隐藏规则和事务；`notifications` 保存提醒并在事务后投递。共享契约只保存实际使用的 DTO、Schema 和校验，不放数据库实体或密钥。

## 5. 预算与记账不变量

- 金额由界面元转换为整数分，服务端验证格式、整数安全范围与允许值；业务日期采用 Asia/Shanghai，不使用设备所在时区决定账目归属。
- 当日未用完额度不自动结转次日。日、月任一额度超出都需要申请，同时超出只生成一次申请。
- 固定支出可按双方事先约定排除日额度，但仍计入月度；申请人不能临时改统计口径绕过审批（D04）。
- 批准一次消费不修改原定预算，也不立即生成实际支出。预算变更保留历史，具体生效和跨月策略依 D03。
- 未审批但已真实发生的消费允许录入并标记；支出录入不会因为预算不足而被直接丢弃。
- 修改、删除保留变更记录；退款关联原支出，不作为额外节省奖励。跨月与多次退款依 D05，关联申请维护依 D08。
- 数据模型至少表达用户、会话、绑定、预算版本、支出及退款关联、申请及状态记录、消息及投递状态；具体字段随对应切片确定，不提前增加全套表。

## 6. 审批状态与一致性

| 当前状态 | 操作与操作者 | 下一状态 | 已确认限制 |
| --- | --- | --- | --- |
| 无申请 | 申请人提交 | 待审批 | 金额、用途、原因与预计消费日期有效；D06、D07 决定额度与时效 |
| 待审批 | 审批人同意 | 已同意待消费 | 保留意见和操作者；不记实际支出 |
| 待审批 | 审批人拒绝 | 已拒绝 | 保留意见；不计算所谓拒绝节省金额 |
| 待审批 | 申请人撤销 | 已撤销 | 原申请保留；金额变化后重新提交 |
| 已同意待消费 | 申请人取消购买 | 已取消消费 | 不记实际支出 |
| 已同意待消费 | 申请人确认实际消费 | 已消费 | 金额不高于批准金额；生成一笔且仅一笔关联账目 |

终态不允许直接重新审批或消费。申请金额变化需要重新申请；实际金额超过批准金额需重新审批，已花掉的部分仍可如实录入并标识未批准超支。具体超额关联和重审操作由 D08 明确，不能简单把批准金额调大。

消费确认在同一个 SQLite 事务中完成权限校验、条件状态更新、唯一关联账目和应用内消息写入，任一步失败全部回滚。远程推送在提交后执行，失败不回滚已经成功的审批。并发同意/拒绝只能一次状态迁移成功；同请求标识的重试与不同操作的状态冲突应区分。

## 7. 自动结余统计

统计集合为本月预算生效后、今天以前的业务日期，不需要每日确认，无支出记录按零支出。

- 累计预算结余 = 集合内每日原定额度总和 − 同口径已录入支出净额。
- 达标天数 = 集合内同口径支出净额不超过当天原定额度的日期数量。
- 结果为负展示累计超支；当天仅展示剩余额度，不提前算入已结束日结余。
- 额度各 80 元的两天花费 60 元和 90 元，应显示结余 10 元、达标 1 天；第三天已结束且无账目时，结余 90 元、达标 2 天。
- 必须显示“按已录入账目统计”，不能把漏记日的零支出包装成已验证的真实存款。
- 补记、退款、更正和删除后重算。分类排除、历史预算和跨月退款口径分别受 D03、D04、D05 约束。

## 8. 契约与验证设计

健康检查和统一错误契约继续复用现有实现。业务请求的路径、字段长度、分页大小、金额上限、会话期限与错误码在对应任务中冻结；本规格不把尚未实现的接口写成已可调用文档。

建议测试 Seam：消费与身份的公开 Interface、Fastify inject、真实 SQLite、跨端共享契约和可控 HTTP Adapter。只断言可观察行为，不断言内部文件拆分。沿用当前配置、应用、数据库和跨端契约测试方式。

测试边界与任务拆分目前为待评审方案，不声称已经获得 TDD 测试边界确认；具体场景见 [验收计划](./验收计划.md)。
