## 1. 本地已完成

- 实际日/月净支出达到 80%、100% 各记录一次；跨两档只发高档，低档视为处理。更正、退款、删除及预算变化不会清除阈值历史；批准未消费不触发实际支出提醒。历史补记按消费日及原月检查。
- 每位用户可关闭系统推送，应用内消息及未读记录始终保留；消息详情只允许收件人读取，点击重新查询预算或申请。
- 推送设备绑定可信用户及当前会话；退出/重置密码通过外键移除设备和待投递任务，过期会话停止投递，重新登记会清除过期占位。有效的其他用户绑定不能被接管。
- 业务、应用内消息、阈值记录和投递队列在同一个 SQLite 事务提交。HTTP 响应后和 30 秒后台扫描处理队列，不在业务事务内等待远程网络。
- 失败保存通用错误并按 30 秒至 1 小时退避重试，用户可请求重试自己的失败通知；重启读取原队列，超过 3 天的旧消息或关闭的投递跳过。服务受理不代表设备到达，已发出的通知无法追回。
- 仅向已授权且登记的设备创建新任务；后续启用设备不会补发过去的消息。原生端用户主动同意后才登记；浏览器显示不支持手机后台推送。

## 2. 真实配置步骤（待执行）

1. 从手机设置记录两部手机的具体型号、完整系统版本；核对华为是否支持安卓 APK 或需原生鸿蒙。
2. 安装匹配项目编译链的 HBuilderX，建立自己的 DCloud AppID。按目标平台开通 uni-push 2.0、包名/BundleName、签名和小米/华为厂商推送通道。原生鸿蒙另需 DevEco Studio 及签名。当前 manifest 的 AppID 仍留空，不填虚构值。
3. 账号开通后，在 HBuilderX 为对应平台启用 Push/uni-push 2.0 模块并打自定义基座/签名包。仅 `npm run build:app` 不产生 APK/HAP，也不能初始化真实推送 SDK。不能只用在线透传替代离线厂商通知。
4. 在自己的 uniCloud 服务空间创建 `bossok-push` 云函数，将 `server/unicloud/bossok-push/index.js` 和 `package.json` 放入对应云函数，启用 `uni-cloud-push` 扩展。将同目录 `bossok-push-receipts.schema.json` 放入服务空间的 database 目录并部署：此表拒绝客户端访问，只供云函数记录受理回执。
5. 云函数环境变量：`BOSSOK_APPID` 为真实 DCloud AppID；`BOSSOK_PUSH_TOKEN` 为至少 32 字符随机密钥；`BOSSOK_PUSH_CATEGORY` 为厂商认可的消息类别 JSON（鸿蒙通道必填，按业务和平台审核选择，不填占位类别）。将云函数 URL 化为受控 HTTPS 接口。未授权请求必须返回 401，不允许变成公开任意设备群推入口。
6. 自建服务环境配置 `PUSH_GATEWAY_URL` 与相同密钥 `PUSH_GATEWAY_TOKEN`，重启生效。密钥只在服务端/云函数环境中，不能放入 App、仓库或截图。云函数只接受任务ID、CID和消息ID；通知内容统一泛化提示，不发送金额、用途或备注。
7. 手机登录后在“我的”同意启用本机提醒，在系统设置中自主授权。返回应用刷新设备状态。两部手机需访问同一可达服务；电脑 localhost 不是手机可达地址。

原生端配置要以实际设备为准；本次未替用户开通付费云资源、部署云函数或上传签名凭据。

## 4. 投递边界

云桥保存受理回执，并对同一投递使用稳定厂商请求标识。厂商已受理但云端回执写入失败时，状态仍不确定：本地保留失败，不伪造成功，需要核验云函数/厂商记录后处理，不能无限改任务ID重新群发。系统权限、厂商省电/自启动策略和网络均影响到达，本实现不承诺必达。

回执只含任务ID、CID、消息ID及受理时间，需随业务备份并由服务端管理。当前仅两人、单服务实例，不引入 Redis 或消息中间件。
