# 老板批了：技术方案与开发计划

- 日期：2026-10-23
- 状态：技术方案已进入工程初始化阶段；具体运行方式见 [README](../README.md)
- 产品依据：[核心产品需求](./核心产品需求.md)
- 架构约束与当前目录：[架构设计](./架构设计.md)
- 目标：服务两个人，完成安装、绑定、记账、审批、结余反馈的完整闭环。

## 1. 推荐技术栈

| 部分 | 建议选择 | 原因 |
| --- | --- | --- |
| 手机端 | uni-app + Vue 3 + TypeScript | 以一套主要页面代码覆盖安卓和鸿蒙，具体能力仍需分平台验证 |
| 界面 | uni-app 内置组件 + 简单样式 | 当前主要是列表、表单、金额卡片，先不增加大型 UI 或图表库 |
| 页面状态 | Vue 响应式状态，按需使用 composable | 当前规模无需先引入全局状态框架 |
| 接口服务 | Node.js 24 + TypeScript + Fastify | 同一语言维护手机端与服务端，服务规模小，模块按业务拆分即可 |
| 数据库 | SQLite + better-sqlite3 + SQL 迁移文件 | 单台服务、少量用户，维护简单；业务数据统一放在服务端 |
| 接口规范 | HTTP JSON API，Fastify JSON Schema 校验 | 服务端统一检查金额、日期、权限和状态，不信任客户端计算 |
| 登录 | 第一版账号密码 + 服务端可撤销的随机会话令牌 | 不引入短信或第三方登录依赖；密码仅存安全哈希，令牌保存摘要和过期时间 |
| 测试 | Vitest：预算规则、统计与接口集成测试 | 重点验证金额和审批事务，接口可用 Fastify inject 测试 |
| 开发与打包 | macOS + HBuilderX；鸿蒙另需 DevEco Studio | 安卓与鸿蒙分别构建、签名和真机验证 |
| 提醒 | 数据库内消息 + 应用内未读提示；系统推送优先评估 uni-push 2.0 | 应用内先保证可查询，后台推送单独完成配置与设备验收 |
| 部署 | 单台服务器 + HTTPS 反向代理 + Node 服务 + 持久化数据库目录 | 第一版只部署一个服务实例，安排数据库一致性备份与恢复演练 |

Node.js 24 已由用户确认。工程使用 npm workspaces 和统一锁文件管理依赖；手机打包工具、签名与真机兼容性仍需另行验证。

SQLite 放在服务端本地磁盘，不能让两部手机直接访问数据库文件，也不能放在多实例共享的网络文件系统中。只有出现多实例或明显并发写入需求时，再评估 PostgreSQL。

## 2. 安卓与华为手机的交付方式

第一项工作是记录两部手机的型号和完整系统版本，并做一个包含登录表单、网络请求的最小应用进行安装验证。

- 支持安卓应用的目标设备：构建签名 APK，并验证安装和覆盖升级。
- 需要原生鸿蒙应用的目标设备：使用 uni-app 的 App-Harmony 构建路径，配合 DevEco Studio 工具链完成签名及真机安装；HAP 调试安装和应用市场发行是不同流程。
- 不假设同一个 APK 可安装在所有华为手机上，也不把浏览器预览通过等同于手机适配通过。
- 尽量复用页面与接口；通知、权限、安装和系统交互按平台适配。
- 签名文件、密码和推送密钥不进入仓库，备份正式签名以支持后续更新。

uni-app 官方提供 Vue 3 鸿蒙开发和独立运行、发行流程，但这不表示所有组件和插件跨端行为相同。需要在开始大规模页面开发前验证实际设备。

## 3. 系统结构

```text
申请人手机 / 审批人手机
        │ HTTPS API
        ▼
同一个 Fastify 服务
  身份与绑定 / 预算 / 记账 / 审批 / 统计 / 提醒
        │
        ▼
SQLite 数据库 + 备份
```

服务端是预算、账目和审批状态的唯一可信来源。手机端负责展示、输入和交互，提交成功后刷新相关数据。第一版不做离线写入与冲突合并；网络失败保留输入并允许重试，不能显示为已经提交成功。

应用进入前台、打开审批页、提交操作后刷新数据；可在前台审批页短间隔刷新，不依赖持续后台连接。系统推送只提示有变动，点击后重新请求服务端，不直接把通知内容当作审批结果。

## 4. 业务模块与数据

| 模块 | 核心数据 | 职责 |
| --- | --- | --- |
| 身份与绑定 | 用户、会话、绑定关系、邀请码 | 登录、角色、两人关系、访问范围；邀请码有有效期且只能使用一次 |
| 预算 | 月度预算、日额度规则、分类适用范围、生效日期 | 保存历史规则，预算变更不覆盖过去 |
| 账本 | 支出、关联退款、申请关联、变更记录 | 查询、记账、更正、可追溯删除、退款 |
| 审批 | 预计金额、消费日期、原因、状态、审批意见、状态变更记录 | 申请、审批、撤销、取消和实际消费确认 |
| 提醒 | 收件人、事件、已读状态、推送结果 | 保存待审批和审批结果消息；推送失败不丢业务数据 |

统计先通过查询计算，不额外维护一份累计余额表，避免账目变化后产生两份不一致的数据。历史账目变更保留可追溯记录，删除采用可恢复的逻辑删除。

金额在服务端和数据库使用整数「分」，界面显示「元」。消费所属日期按 Asia/Shanghai 的业务日期保存，操作时间保存统一时间戳。客户端输入必须校验最多两位小数，不能依赖浮点金额直接累加。

## 5. 必须先实现正确的规则

1. 每个接口验证当前用户与绑定关系；审批人角色由服务端确认，不能接受客户端自行传入角色获得权限。
2. 日额度和月预算一起判断；固定支出仅按预先约定的分类规则排除日额度，仍计入月度支出。
3. 原定额度按生效日期保留；预算调整是否允许当日生效需先确认，不能追溯美化已结束日期。
4. 审批状态迁移用条件更新，阻止重复审批；确认消费与创建关联账目放在同一数据库事务中。
5. 同一申请只能生成一笔消费账目，数据库加唯一约束；新增记账和提交申请使用客户端请求标识防止网络重试造成重复。
6. 超过批准金额需重新审批，已真实发生的支出仍可记录并标记。未消费申请跨日如何处理需在实现前约定。
7. 累计结余自动统计本月预算生效后已结束日期的已录入账目，扣掉超支日；无记录按零支出，不设每日确认状态。补记、修改、退款后重新计算，退款按原支出归属口径修正结余；界面注明按已录入账目统计。
8. 推送在事务提交后触发，发送失败不回滚已经完成的审批；应用内消息是可查询记录。第一版可用消息表记录待发送和失败状态，不另建消息队列。

多笔已批准未消费申请是否占用可申请额度、有效期和跨日处理仍是待确认的产品规则；技术实现不擅自选择口径。至少必须展示未消费申请总额，避免审批人忽略已经作出的承诺。

## 6. 推荐开发顺序

| 阶段 | 工作 | 验收结果 |
| --- | --- | --- |
| 0：设备验证 | 核对手机系统，最小应用打包安装，验证请求和通知配置可行性 | 确定 APK 或安卓与鸿蒙分别交付的路径 |
| 1：规则与界面 | 细化预算生效、跨日申请、未消费额度、解绑规则；画五个页面与关键状态 | 确定计算口径与审批状态，避免后续返工 |
| 2：基础闭环 | 登录、绑定、预算、快速记账、账本与首页剩余额度 | 两部手机访问同一服务，看到一致数据 |
| 3：审批闭环 | 发起申请、同意拒绝、撤销、消费确认、重复提交保护 | 完成一次真实的超支申请到关联记账流程 |
| 4：节省反馈 | 自动统计累计结余、达标天数、补记退款重算 | 通过产品文档中的计算示例、无记录日期和补记场景 |
| 5：提醒与发布 | 应用内提醒、系统推送、HTTPS 部署、备份、正式签名包 | 真机验证前台、后台、权限关闭、断网重试、安装升级 |

应用内提醒可以先完成闭环；手机后台推送属于完整第一版的验收项，不能以应用内刷新代替后台提醒。

## 7. 最小验证清单

- 单元测试：日、月预算边界，固定支出排除，结余为负，当天与预算生效前日期排除，无记录日期按零支出，历史规则生效，补记与退款重算。
- 接口集成测试：越权访问、过期会话、邀请码重复使用、重复审批、重复消费确认、事务失败不产生半条数据、重复请求只记一次。
- 两角色真机测试：提交申请、审批、消费确认后双方一致；网络失败保留输入；应用重开获取最新状态。
- 发布测试：签名安装与覆盖升级不丢数据；备份可恢复；推送未授权或失败时仍能在应用内看到消息。

## 8. 建议代码目录

具体目录与依赖规则以 [架构设计](./架构设计.md) 为准。预算、账本、审批和汇总作为消费 Module 内部能力，共享事务；身份、通知和健康检查独立组织。

```text
BossOK/
  docs/                 产品需求、技术方案
  app/                  uni-app 手机端
    src/pages/          首页、账本、审批、月度汇总、我的
    src/features/       功能 Module
    src/shared/http/    HTTP 请求与错误处理
    src/platform/       平台 Adapter
  packages/contracts/   前后端共享类型、Schema 与校验
  server/
    src/modules/        健康检查；后续增加身份、消费与通知 Module
    src/infrastructure/ SQLite 初始化与迁移
    migrations/         数据库迁移
    tests/              后端行为、跨端契约与架构规则测试
```

第一版无需微服务、Redis、工作流引擎、独立后台管理系统或单独的两套手机端。审批人功能放在同一个应用中，暂不添加与当前需求无关的基础设施。

## 9. 开发前所需信息与资源

- 双方手机型号和完整系统版本；决定是否需要鸿蒙独立构建。
- 预算初始值及第 5 节未定规则；确定后补充产品文档。
- DCloud 开发账号；如需鸿蒙，准备对应工具链、签名与目标分发方式。
- 可供两部手机访问的 HTTPS 服务地址、服务器与数据备份位置。
- 系统推送所需账号、平台参数与通知授权；先核对平台要求，凭据不写入文档或源码。
- 本方案不预估固定工期或报价，需先验证设备和签名分发路径；服务器、通知及分发服务的费用按实际选择核实。
