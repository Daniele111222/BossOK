## 3. 必须覆盖的反例

- 恰好等于日/月预算不被误判超支；超一分钱应按正确口径识别。超出允许范围、精度错误和无效业务日期应被拒绝。
- 未绑定、会话过期、非本人账目、非当前关系申请、伪造操作者均不能读写不属于自己的数据。
- 网络超时不等于服务端未写入，必须用相同请求标识验证重试结果；不同操作的并发冲突不能当作同一次成功。
- 先批准后不购买不记支出，也不把批准/拒绝的申请金额当作节省。
- 当天、跨月、预算首次生效和预算变更前后的统计各有独立案例，按确认的历史版本计算。
- 应用关闭或通知权限关闭不影响服务端审批结果，重新进入应用仍能读到最新状态。

补充已确认的验证场景（分别归入现有编号，不增加新需求）：

- A01/A02：会话 7 天过期，重置密码撤销旧会话；邀请码 24 小时失效，角色不可自提权，无换绑/解绑入口。
- A03/A04：预算首次当日生效，日额度修改次日生效，月预算立即修改留轨迹；跨月沿用不结转，首月不自动折算。
- A06：部分/多次退款不超原额，跨月退款重算原消费日；有退款不删除，修改原金额不低于累计退款。
- A07/A08：批准承诺从可安排额度中扣除，待审不占用；实际支出与承诺展示分离，批准例外不修改原预算。
- A09/A10：当日过期释放占用，跨日购买重申，批准当日已消费次日可补记；批准 100 元实际 120 元仅记一笔 120 元，20 元补批不再新增支出。
- A13：日/月 80%/100% 各一次，单次跨两档只发高档，更正反复跨档不重复提醒；阈值只看实际支出，关闭推送仍有应用内消息。

## 4. 发布完成条件

1. 第一版 R01—R12 的验收全部有结果，已确认 D 项规则符合结果，暂缓的设备与部署参数已在对应交付阶段落实。
2. 自动化、构建及真机证据可定位；不能用工程的 20 项历史测试代替新增业务测试。
3. 未解决问题明确影响与处置，不能把未经处理的权限、事务、数据恢复问题标记为可发布。
4. 依赖审计单独记录，当前 README 的历史风险仍有效，构建通过不等于风险已解决。
5. 正式安装包签名、服务地址、数据库备份和恢复说明齐全；不要求第一版必须上架应用商店。
